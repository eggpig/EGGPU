# Related Work：两部分正文骨架与论证脉络

更新：2026-11-04。按用户本轮要求，仅提供可继续润色的正文骨架与故事顺序，不代替最终英文正文、引文选择或参考文献表。本文件不包含新的性能结论。

## 1. 总线索

**给定任务怎么执行得快 → 连续任务中哪些工作可以复用 → 输入、函数和内存约束共同变化时，如何维护并保留合法执行状态。**

这里的“假设”指一类工作的主要优化前提和问题边界，不表示这些论文都明确写出了同一个假设，更不表示它们没有考虑边界外的问题。每组先交代为什么该前提合理，再说已有工作解决了什么，最后把讨论推进到本文关心的成本。

两部分建议使用 **GPU-Accelerated Graph Processing** 与 **Graph State Maintenance and Reuse**。每部分约两个自然段，总篇幅先按约半页到四分之三页安排，随最终版面调整。不要把六个论证台阶写成六段带作者名字的文献清单。

## 2. 第一部分：GPU-Accelerated Graph Processing

### 应当怎样讲

1. **第一类工作把图和分析任务视为给定输入，主要优化并行执行的效率。** 从 frontier、负载均衡和访存讲到多 GPU 工作分配与通信。Gunrock、SYgraph、Groute、GUM 可分别承担接口、设备执行和多卡协调的证据；cuGraph/nx-cugraph 作为实际软件生态入口简述即可。
2. **第二类工作把设备容量和数据供给视为主要限制，重点减少等待图数据的成本。** 接到显式传输、零拷贝、工作集选择以及 CPU–GPU 协作。EMOGI、Subway、HyTGraph、CGgraph 可按所解决的瓶颈一起叙述，不必逐篇展开实现。
3. **第三类工作进一步利用任务和数据的持续性，减少连续处理中的重复工作。** C²graph 处理多查询的 CPU–GPU 协作，Grapin 结合流式更新、依赖维护和子图缓存。这一步必须承认相关进展，随后自然提出本文的具体问题：当函数切换、属性版本更新和图回访同时出现，执行状态的合法性与物理驻留如何共同影响完整任务成本。

### 中文正文骨架

GPU 图处理的早期研究主要关注：给定图和分析任务后，如何使不规则计算有效利用设备并行性。相应系统围绕活跃顶点组织、线程负载均衡和图数据布局改进执行效率，并逐渐扩展到多 GPU 间的任务分配、通信和动态负载协调。与此同时，通用 GPU 图分析库将这些能力暴露为可组合的算法接口，降低了应用使用加速器的门槛。对于超过设备容量或受到数据供给限制的图，另一类工作则把重点放在主机与设备间的数据移动，通过选择传输方式、压缩或筛选工作集以及协调 CPU 与 GPU 执行，减少访存等待和重复传输。

这些研究的优化对象也已从单次执行扩展到连续任务。多查询协作可以利用不同查询的执行阶段差异，流式图处理可以在图更新后复用合法状态，并缓存持续活跃的子图。因此，连续处理本身并不是本文区别于已有工作的充分理由。本文进一步研究的是：在多种分析函数交替执行、图属性产生新版本以及有限显存中的图回访同时发生时，如何共同管理这些函数需要的执行视图。快速执行一个已经准备好的任务仍然重要，而视图是否仍然有效、需要维护哪些物理数据、以及哪些状态值得继续保留，也会决定整段分析任务的完成时间。

## 3. 第二部分：Graph State Maintenance and Reuse

### 应当怎样讲

1. **第一类工作认为变化的主要成本可以通过改善存储布局和局部更新来降低。** 以动态邻接存储、重建、连续扫描之间的折中为起点。GRACE、Terrace、LiveGraph 是这一层的材料；不要把其拓扑更新写成本文已经实现的能力。
2. **第二类工作认为已有状态只要具有一致版本或可追踪依赖，就能安全用于后续计算。** 分清复用对象：Aspen/GraphOne 的图快照或视图，GraphBolt 的依赖和中间计算，KGraph 的查询结果片段，Shared Arrangements 的跨查询共享索引。此处重点不是“谁用了缓存”，而是“复用什么，何时仍然合法”。
3. **第三类工作进一步考虑有限内存，按需求、依赖和恢复成本决定保留对象。** PACMan、LRC、Blaze 已经说明逐对象命中率、最近访问时间并不足以刻画完整任务收益。承认已有依赖感知缓存与共享状态生命周期管理，然后落到本文的物理对象关系：一个逻辑视图被撤销，不一定释放其名义大小的显存。

### 中文正文骨架

图状态维护研究首先面对更新效率、查询局部性和一致性之间的折中。一类系统通过动态邻接表示和局部重建降低结构变化的成本；另一类系统通过持久快照、版本管理和共享视图，使查询能够在更新发生时继续读取一致状态。在此基础上，增量图处理与并发查询系统进一步利用依赖关系或可复用的局部结果，减少后续计算中的重复工作。已有流式数据流系统还支持跨查询共享索引，并协调多个读者对同一物理状态的持有与回收。因此，共享状态、引用计数和旧读者保护本身都不应作为本文的新颖性主张。

有限内存使状态复用进一步转化为保留决策。相关缓存研究已经根据任务需求、依赖关系以及重新计算或恢复的成本选择保留内容。本文关注这一问题在 GPU 图执行视图上的具体形式：不同函数和版本可能共同持有同一组拓扑或属性数组，因此逻辑视图的大小与撤销该视图后实际释放的空间并不相同。同时，一个被保留的合法版本还可能成为后续属性维护的基础。D-Maintain 根据数据与函数依赖选择合法的维护路径，C-Retain 根据物理共享关系计算实际可释放空间并选择保留状态；我们评估它们如何影响同一资源约束下完整分析任务的维护、重载和执行成本。

## 4. 最后收束时保持的具体边界

- 本文当前 D 的核心是固定拓扑下 FP64 权重版本及相关执行视图的维护；不能写成通用拓扑插删，或声称更新后不再完整执行图算法。
- C 当前使用历史需求和真实可释放字节形成启发式评分；不能写成具有实测恢复毫秒成本的最优缓存规划器。
- Grapin 已有更新与缓存，KGraph 已有跨查询结果复用，Aspen 已讨论跨算法摊销快照构建，Shared Arrangements 已有实际物理共享与读者生命周期，LRC/Blaze 已有依赖感知缓存。区别应落到具体对象、合同和实测收益，避免“现有工作都只处理单查询”“此前都将缓存对象视为独立”等概括。
- 单卡和多卡是执行资源范围；D 和 C 是连续分析中的状态管理问题。两部分 Related Work 按研究问题组织，不按单卡一段、多卡一段，也不把 D/C 分别写成互不相干的两个研究领域。
- 原 VLDB 稿的 cuGraph 相关条目实际是 nx-cugraph 官方文档。可以继续引用该软件入口，但不要把文档写成一篇 CCF A/B 论文；Gunrock 的旧稿期刊版与 PPoPP 会议论文也要在最终参考文献中区分。

最终写作的过渡句可以保留这一意思：**已有研究已分别改进执行、维护和复用；本文研究它们在连续图分析中通过版本、函数依赖与物理共享发生耦合时，如何减少正确完成任务的总代价。** 这是一项待实验支撑的具体定位，不能替代对强相关系统的比较。
