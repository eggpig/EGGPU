# Introduction 中文稿

修订：2026-11-06。P1–P6 仅用于组织段落，排版时删除。正文结果句须由同源实际测量填入；首页图采用四请求轨迹；配对主时间从初始 G⁰ 已就绪后的权重提交开始。

**P1｜研究背景。** 图分析是社交网络分析、路径规划和关系数据挖掘的重要基础。[GUM] 在这些应用中，一次计算往往只是分析过程中的一步：应用可能在同一张图上继续查询，在数据更新后重新计算，也可能切换到另一张图，再返回此前处理过的图。GPU 的并行计算能力为这类分析提供了加速手段，多 GPU 执行进一步扩展了可利用的计算和存储资源。随着请求连续到来，系统需要处理的不仅是每次算法的执行，还包括供这些算法使用的图状态如何延续。

**P2｜已有进展与剩余瓶颈。** 现有 GPU 图处理研究已通过改善任务分配、访存和设备间通信提高计算效率。例如，GUM 利用远程工作窃取缓解多 GPU 执行中的动态负载不均和长尾停顿；动态图系统 GRACE 则通过限制重建和数据移动的范围，降低图更新的准备成本。[GUM；GRACE] 然而，在连续分析中，**图状态会被持续复用、更新和回访，而 GPU 显存是有限的**。图 1(a) 给出一个具体过程：先在 $G^0$ 上运行最短路径，修改部分边权后在 $G^1$ 上再次运行，随后处理另一张图 $H$，最后回到 $G^1$。计算之间，系统需要将新权重送入正确的设备表示；切换至 $H$ 后，保留状态可能超过预算，需要释放其中一部分，而回访又可能需要重新准备这些状态。图 1(b) 在初始 $G^0$ 已就绪后，从权重更新开始计时，比较两种状态管理策略对连续会话时间的影响。在相同请求、执行后端和保留预算下，Full upload + LRU 与 EGGPU 分别用时 8.94 s 和 7.90 s（一次配对观测）；其中，主机权重提交与输入准备分别占两臂时间的 79.9% 和 74.5%，是本例的主要成本。即便两种策略已共享不变拓扑，并避免对新权重再作全量合法性验证，完整权重数组的重建与内容哈希仍有 $O(m)$ 成本，状态准备仍占据大部分会话时间；改进单次算法执行并不能消除这些成本。维护与保留因而需要在完整请求序列中共同考虑。这要求解决两个相互关联的挑战。

**P3｜挑战一：为当前请求维护正确且可复用的图状态。** 一次更新并不意味着已有状态全部失效。在上述例子中，$G^0$ 到 $G^1$ 只改变边权，邻接关系仍然可用；SSSP 需要新权重，而只读取拓扑的 BFS 不受该更新影响。同一条边在按出边和按入边组织的表示中又可能对应不同位置，所以逻辑上的一次修改，需要落实到当前函数实际使用的表示。维护方式还取决于旧状态是否仍被使用：目标存储可独占修改、且无需保留旧值时，可以原位维护；旧读者仍需访问原值时，则必须为新版本准备独立存储。系统因而需要同时识别函数依赖、版本和设备上的已有状态，准确确定哪些可以继续使用、哪些必须维护，并保护旧请求的读取语义。把每次变化都处理成整份状态的重新准备会增加重复工作；只检查图名称或版本号，又不足以确认某个设备表示是否可直接使用。

**P4｜挑战二：在有限显存中决定保留什么，并释放实际可用的空间。** 处理完一个请求后，保留其状态能够帮助后续回访，却也占用有限的显存预算。这一选择不能只看状态的最近访问时间或名义大小。两个图版本可以共享同一份拓扑，只分别保存自己的权重；此时撤销一个版本，并不能释放仍由另一个版本持有的拓扑。切换至 $H$ 后能回收多少空间，取决于底层分配还有哪些持有者，而回到 $G^1$ 时需要恢复多少内容，又取决于哪些状态得以保留。系统需要在请求完成边界识别允许撤销的状态集合，计算它们在每个设备上实际能释放的字节，并结合后续需求的历史信息作出选择。这个挑战与前一个挑战紧密相连：维护决定哪些存储继续共享，保留和释放决定后续请求能够复用哪些状态。

**P5｜方法与系统。** 我们提出 EGGPU，将请求到来时的图状态维护与请求完成后的状态保留连接起来。EGGPU 记录图版本、表示和设备状态之间的内容依赖，以及这些状态对底层分配的持有关系。D-Maintain（依赖感知维护）根据当前请求识别仍然有效的输入，仅维护受影响的部分，并按照旧状态的持有情况选择原位更新或复制后更新。在完整结果取得独立所有权后，C-Retain（闭包感知保留）沿完整持有关系构造合法撤销集合，以每个设备实际可释放的字节检查保留预算，并结合历史需求选择保留对象。两种机制共享对状态关系的描述，使当前维护所形成的共享能够进入后续回收决策。系统将它们与适用的单 GPU 和多 GPU 执行路径结合；BFS、SSSP、PageRank 等算法仍执行完整计算。

**P6｜验证与贡献。** 我们以固定来源的七张道路、社交和网页图组织评估，分别考察同资源的系统比较、固定后端的多 GPU 强扩展、请求内状态维护、跨图保留、两种机制的联合效果，以及包含扩展函数的依赖应用。比较使用完整结果与明确的计时边界；机制实验同时记录维护量、实际分配释放和会话时间，区分减少数据移动与缩短完整任务的效果。本文的主要贡献如下。

1. **依赖感知的图状态维护。** 将函数、版本和设备表示的依赖与旧状态持有约束结合，确定可复用输入和合法维护范围，并实现固定拓扑权重更新中的原位维护与复制后维护。
2. **依据实际释放量的状态保留。** 由物理分配的完整持有关系确定合法撤销集合，按逐设备实际可释放量满足保留预算，并利用历史需求指导选择。
3. **连续图分析系统与评估。** 在 EGGPU 中连接上述两种机制与单 GPU、多 GPU 执行路径，通过系统比较、受控机制实验和依赖应用检验其收益及适用边界。

## 编辑说明：不进入论文正文

- **首页证据状态。** 当前图 1 已绑定[真实配对回执](../../provenance/first_page_unified_summary.json)，完整输出与实际预算压力均通过检查。初始 G⁰ 就绪后的主时间为 8.938643417 s 与 7.899269512 s，即本次 EGGPU 少用时约 11.6%；不将一次配对差异写成稳定加速比。旧版本较慢的观测仍保留在实验原始记录中。IN/UK 请求序列是受控实验，不是业务日志；n=1 不支持稳定性或普遍收益的结论。
- **结果边界。** 主窗口按用户 ready 后计时要求，在第二臂返回前固定；原四请求总时间与阶段保留在补充记录。不能将末次回访的改善冒充全序列收益，准备占比来自另行核对的互斥实测阶段，不是从两根总时间柱推断；仅说明这一实例，不能概括为所有图的规律。P6 完整结果句待当前 E1–E6 证据齐备后填写；不要先写系统普遍领先、所有函数多卡单调加速或 D/C 时间协同。
- **对照身份。** `Full upload + LRU` 对应 `persistent_full + closure_lru`：它保留主机内存中的版本提交并具有正确的分配闭包记账，并非每次全图重建，也不是全部机制关闭。`EGGPU` 对应 `lease_sparse + closure`。首页两臂改变 D 与 C 两项策略，只展示联合选择下的实际差异；D/C 各自作用由 E3–E5 区分。
- **权重提交成本。** 此处 `validation_edges=0` 仅说明省去了新权重的全量合法性验证；完整权重重建与内容哈希仍为 $O(m)$，不能表述为消除了所有全量扫描或使整个提交成为稀疏复杂度。
- **D 的范围。** 当前稀疏复制后维护／lease 路径主要针对固定拓扑的 FP64 权重；拓扑变化和不同静态执行路径在方法节分别说明。不声称增量更新算法答案，也不声称所有派生状态均只需常数次修改。
- **C 的范围。** 预算约束在请求完成边界检查，覆盖受管保留状态，不等于峰值显存或进程总显存上限。历史需求评分是无量纲指标，不是实测恢复时间模型，也无全局最优保证。不得把受管预算压力写成物理设备 OOM。
- **新颖性。** 快照、引用计数、共享索引和依赖感知复用均有先例。论证集中在连续 GPU 图分析中，输入依赖与物理持有关系如何共同决定合法维护、逐设备释放与后续恢复。
- **图位。** Fig. 1 只承担具体请求场景和初始状态就绪后的实测会话时间；机制图与系统框架图保留协作者的位置，最终编号在排版时确定。
